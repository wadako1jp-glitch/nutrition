# データソース調査（学校給食レシピ）

## 結論
「自治体標準オープンデータセット（旧・推奨データセット）」の **「学校給食献立情報」** 形式で公開している自治体のデータを使う。
料理ごとに材料が **食品番号（成分表）＋分量(g, 児童1人分)** で入っているので、アプリの用紙にそのまま流し込める。
ライセンスは CC BY 4.0（出典表示で商用利用可）。

## 標準形式の主な列（豊中市CSVで確認）
提供年月日 / 献立ID / 料理ID / 料理名称 / 同一料理内通し番号 / 食品ID / 食品名称（成分表） / 食品名称（独自） /
分量 / エネルギー / たんぱく質 / 脂質 / 食塩相当量 / カルシウム / 鉄 / ビタミンA_ugRAE / ビタミンB1 / ビタミンB2 / ビタミンC / 食物繊維 /
炭水化物 / アレルゲン品目 / 調理方法 / 備考 / **食品番号** / 枝番

## 取り込み方針
- 使うのは「料理名称・食品番号・食品名称・分量」だけ。栄養価列は自治体側ソフトの計算（成分表の版が不明）なので使わず、八訂で再計算する（答え合わせ用に残してもよい）
- 食品番号は先頭ゼロ落ち（例: 1083 → 01083、13003）。5桁ゼロ埋めして八訂と突合
- 1人分(g)で入っているので、用紙に入れるときは人数を掛ける
- ビタミンDは標準形式に無いが、八訂再計算で埋まる
- 食品番号が空/独自名のみの行は表記ゆれ辞書で八訂に紐付け（残りは手当て）

## 訂正: 学校給食献立情報は「一般的なレシピ」に不向き
調理実習の実物サンプル（data/samples/）を見ると、対象は家庭料理（揚げ物・洋食仕立て・蒸し料理・郷土料理、1〜4人分）で、
給食データ（子供の摂取基準に合わせた大量調理メニュー）とは対象・分量とも別物と判断。
学校給食献立情報は、当初の設計どおり**有料機能「学校給食基準の献立参照」専用**に位置づけを戻す。
無料の「一般的なレシピ」の代替候補: 農林水産省「うちの郷土料理」（都道府県別、材料・分量つき）。
「日常食」系（揚げ物・洋食・蒸し料理等）に合う汎用レシピの公式オープンデータは未発見、要継続調査。

## 重要な発見: 調理による重量変化が必要（廃棄率とは別のマスタ）
実物サンプルで判明: 「使用量(g)」と「栄養計算に用いる食品重量(g)」が食品によって大きく異なる。
例: 精白米80g → 「精白米・めし」168g（生→炊飯で吸水増加、成分表の食品コード自体が変わる）
    たけのこ(ゆで)20g → 18g、おろししょうが1g → 0.24g（絞り等による使用量からの歩留まり）
これは廃棄率（購入量⇔可食部）とは別の、八訂付録「調理による重量変化率表」に基づく変換。
→ データ基盤にもう1つ表が必要。米・いも・乾物の戻し・おろし物など、変換が起きる食品を洗い出す必要あり。


## 検証結果（用紙4枚・約84語で実施）
「栄養計算時の食品名」列の語を成分表2,538件と突き合わせ:
- 素のトークンマッチ（・区切りの部分一致）で **86%** ヒット
- 残り14%の内訳はデータの欠落ではなく、ほぼ全て「学生が書く漢字表記」と「成分表の公式ひらがな表記」のズレ
  （例: 濃口醤油→こいくちしょうゆ、牛→うし、鶏→にわとり、にんにく語順）
- 20〜30語程度の**固定変換リスト**（`data/synonyms/common-terms.py`に seed 済み）を1層加えるだけで、検証した範囲はほぼ100%ヒット
→ 当初想定していた「AI大量生成による3層目」は不要、または優先度低。表記ゆれ対策は「かな正規化＋固定変換リスト」で大部分をカバーできる見込み
- 同一名が複数品種にヒットする曖昧さ（例: にわとり もも 皮つき 生 → 親／若どりの2件）は検索候補を複数出すUIで解決（既存の設計方針のまま）

## 検証結果2: 使用量→栄養計算重量のパターン分析（用紙4枚・約90行）
- 約80%は変換なし（使用量＝計算重量）
- **生米→めし変換の比率は一定ではない**: 青豆ご飯80g→168g(2.10倍)、ちらし寿司100g→210g(2.10倍)、鶏めし(炊き込み)75g→137.5g(1.83倍)
  → 公式の重量変化率表の値は「デフォルト」として使い、レシピごとに上書きできる設計（既存方針どおり）が実データでも裏付けられた
- おろし生姜 1g→0.24g が2箇所で同一比率で再現 → 再現性のある個別係数は見つかり次第、辞書に先回り登録する価値あり
- 合挽き肉の「牛6:豚4」表記はレシピ設計上の按分であり、アプリでは牛肉・豚肉を別々の行として直接グラム入力すればよいだけ。按分計算機能は不要
