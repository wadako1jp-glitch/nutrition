# 意思決定ログ

- 一次ターゲットを栄養管理課程の学生に決定（教育用途で押す）
- 成分表データは改訂対応前提でバージョン管理する方針とした
- 市場は小さいと認識。重視するのは「痒いところに手が届くか」と開発予算とのバランス
- 献立管理・記録保存は業務用途にしないためスコープ外とした
- DBは使わず、成分表をインメモリで扱う方針に決定（パフォーマンス最優先の要望を、この規模ではDB選定ではなく実装レベルの工夫で満たす）
- 一般的な献立は文科省・学校給食関連の公的な献立基準データを参照データとして取り込む方針。ユーザー独自の献立作成・保存機能は業務用途にしないためスコープ外のまま
- プロジェクトの一番の狙いは信用構築・実績づくり（Note執筆と同じ路線）と確認。収益は二の次
- 課金モデルを「基本無料＋300円買い切りで一部機能アンロック」に決定
  - 無料: 栄養計算＋塩分%可視化（DL数・実績最大化）
  - 有料300円: 学校給食基準データの献立参照＋発注量算出（差別化機能、マネタイズ実績も兼ねる）
  - サブスク・広告は不採用
- UIは学校の栄養価計算用紙の列構成をそのまま採用（ワークシート型、無骨でよい）。行入力のたびに即時計算
- 食材入力はあいまい検索＋食品番号直打ちの両対応。将来レコメンド機能
- 計算ルール: 小数第1位丸め、可食部ベース、仕入れ量は廃棄率換算、小計は献立ごと
- 出力はオンラインのみ。当面は非公式アプリ（提出は紙へ転記）
- 変更: 献立の保存・編集をスコープに戻す。一般的なレシピのインポート/エクスポートとカスタム（足りない栄養素を補う編集）が必要なため。保存は端末内JSON、バックエンドは引き続きなし
- 公開はv1.0を無料で出し、IAP（300円アンロック）はv1.1で追加する方針
- インポート用の一般レシピは公共データがあれば活用、無ければペンディング。自前でレシピ集を作り込まない
- DB不要を容量で裏取り: 八訂約2,500食品（用紙列＋廃棄率で約0.5MB、本表フルでも1.5MB）、辞書0.3MB、給食レシピ5自治体で0.5〜1MB → JSON計2〜3MB、メモリ5〜10MB。ユーザーデータは2年で数百KB。保存先はAsyncStorage（Android 6MB上限）を避け、MMKVかファイルにする
- 保存先はMMKVに決定（速度・同期APIを優先）。ただし呼び出し側から実装を隠す薄い抽象層をsrc/lib/storage/に置き、将来ファイル直書き等への差し替え要望に対応できるようにする
- 食品解決を1本のパイプラインに統一: 入力は常に(食品名,使用量)、そこから(栄養計算時の食品名,栄養計算重量)を導く。廃棄率換算・調理による重量変化・個別係数（おろし等の慣習値）を種類分けせず同じ「解決ルール」として扱う。個別係数は公式表に出典がないことがあり自動生成不可、用紙サンプルとの答え合わせで手動収集する
- アプリが出す数字は「計算上のPFC・栄養バランス」（学生の手計算と同じ性質の見積もり）であり、物理的な真値の再現ではないと明確化。これにより「栄養計算重量」を常にユーザー編集可能にする方針とし、個別係数（おろし物等の慣習値）の網羅的な先回り収集は不要と判断
- 表記ゆれ対策を軽量化: 用紙4枚・約84語で検証した結果、AI大量生成は不要と判明。かな正規化＋20〜30語の固定変換リストでほぼ全てカバーできる見込み（docs/data-sources.md参照）

- 方針転換: v1はReact Native/Expoのネイティブアプリではなく、スマホ向けWebアプリ（PWA）で様子見。ストア登録・審査が不要で身軽。データのほとんどをDBで持たない構成のため成立する。ネイティブ化は将来必要になれば再検討（先送りであり破棄ではない）
- オフライン対応（Service Workerでのキャッシュ）は最初から作り込む方針に確定。使用場面が調理実習の教室だけでなく自宅なども含み接続環境の強弱を確定できないため、現時点では弱い方に合わせる
- ストレージ実装をMMKVからブラウザストレージ（IndexedDB/localStorage）に変更。`src/lib/storage/`の抽象層のおかげで呼び出し側は無変更で対応可能
