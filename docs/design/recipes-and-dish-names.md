# 設計: 料理データ・献立名の自動付け・献立の検索と取り込み

## 目的
1. 材料から料理名を推定し、献立名を `yyyymmdd_料理名`（例: `20260925_肉じゃが他`）に自動で付け替える
2. 料理を検索して、材料表に取り込めるようにする（学生どうしの共有も含む）

どちらも PWA のまま（サーバーなし・オフライン・運用費0円）で作る。

## 基本方針: 料理データを1つ持ち、2つの機能で使う
```
料理データ（src/data/dishCatalog.ts。アプリに同梱）
   ├─ 材料と見比べる → 献立名の自動付け（今回）
   └─ 検索して選ぶ → 材料表に取り込む（次の段階）
```

### 料理データの作り方
- AI（Claude）が作る側で一般的な家庭料理・給食料理を作り、人が PR で確認してから入れる。画面には「目安」と示す
- 各材料には「食品名の語」（照合用）と「代表の食品番号・1人分の目安g」（取り込み用）を持たせる
- テスト（`tests/dishName.test.ts`）で、食品番号が実在してその語に当たるか、各料理が自分の材料でその料理と判定されるかを確かめる。料理を足したときの取り違えもここで分かる
- レシピサイトの文章・手順は取り込まない（料理名と材料・分量の目安だけ持つ）

### 実行中に AI を使わない理由
| 方式 | 判断 |
|---|---|
| クラウドの AI に問い合わせる | API の鍵を PWA に置けず中継サーバーが要る。オフラインで動かない。費用がかかる |
| 端末内の AI（ローカル LLM） | 数百MB〜1GB のダウンロード、iPhone では動く機種が限られ、遅い。小さいモデルは料理名を外しやすい |
| 料理データとの照合（採用） | 数十KB、全端末で一瞬、結果が毎回同じで理由も示せる |

推定は `inferDishes()` 1か所にまとめてあるので、ローカル LLM が実用的になれば、対応端末だけの追加機能として中身を差し替えられる。

## 献立名の自動付け（今回の実装）

### 推定の仕方（`src/core/dishName.ts`）
- 食品名を語に分け、料理データの材料の語と照合する（語が同じか、その語で終わる。「しょうゆ」→ こいくちしょうゆ）
- 材料の重み: 主な材料 3・よく入る材料 1・調味料 0.5
- その料理と判定する条件: 主な材料がすべて入っていて、重みの合計の半分以上が入っている
- 1つの献立に料理が複数あるので、重みの大きく当たった料理から順に材料を割り当てる（調味料はほかの料理と共有してよい）
- 献立名に使うのは 主菜 ＞ 主食 ＞ 副菜 ＞ 汁物 の順で最初の料理。その料理の材料以外（調味料を除く）が献立にあれば「他」を付ける
- ご飯を別に盛る献立が多いので、「ご飯＋肉＋たまねぎ」だけで決まる料理（牛丼・チャーハン等）は料理データに入れない（別盛りのご飯と肉じゃがを「牛丼」と取り違えるため）

### 自動と固定（`src/screens/worksheet/MenuTitleSelect.tsx`）
- **自動**（新しい献立の初期状態）: 材料が変わるたびに推定した料理名に付け替える。推定できないうちは食事区分（作成時刻から推定した朝食・昼食…）
- **固定**: プルダウンで料理名か朝食・昼食…を選ぶと、以後は材料が変わっても名前を変えない。「自動」を選び直せば自動に戻る
- 保存: `StoredMenu.titleMode`（`auto` / `fixed`）。項目の無い旧い献立は `fixed` として扱い、名前を勝手に変えない

## 次の段階（別PR）
1. **献立の検索と取り込み**: `#/recipes` に料理の検索画面。選ぶと代表の食品番号・目安gで材料表に行を足す（取り込み後に学生が自分の分量へ直す前提）
2. **共有URL**: 献立の材料を URL（`#/import?d=…`）に埋め込み、LINE 等で送ると受け取った人が確認して取り込める。サーバー不要
3. **料理データを増やす**: 成分表18群（調理済み流通食品、55品）の原材料配合割合を公式資料で確認できれば取り込む。ほかは AI 作成＋人の確認で足す
4. **ローカル LLM の試験**: 別ページで小さなモデルを動かし、実機（iPhone）でダウンロード時間・速さ・当たり具合を測ってから採否を決める
